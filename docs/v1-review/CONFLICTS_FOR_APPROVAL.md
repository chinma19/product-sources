# Personal Style Blueprint v1.0 — source conflicts for approval

Status: awaiting owner decisions. No application code, methodology, stored customer answers or live deployment changed during this review.

Read in full: Product Build Specification v1.0 (26 PDF pages); Codex Engineering Build Specification v1.0 (23 PDF pages); approved Clean Master Manuscript Draft 3 (68 customer pages, plus production material). Compared against the existing application source. PDF page numbers below mean the physical attachment page; manuscript numbers mean its approved PAGE NN inventory.

## Proposed authority rule

Use the two v1.0 documents for product capabilities and engineering acceptance. Keep Draft 3 as the authority for approved customer wording, locked consolidations, original examples and exercise content. Apply compatible v1.0 requirements directly. For an actual contradiction or an exercise absent from Draft 3, use the explicit owner decision below. Neither a specification's internal “approved” label nor an old implementation decision substitutes for owner approval of a conflict.

The documents agree on Body + Personality + Lifestyle; the five-part journey; reused evidence sets; self-directed interpretation; no body-type prescription, fixed aesthetic or AI-assigned identity; customer-editable results; and avoiding wardrobe-management scope.

## Decisions requested

### R1 — Front matter, subtitle and baseline

- **Product §06, PDF pp.4–5:** subtitle “A guided system for figuring out how you actually want to dress.” Front matter includes “What Personal Style Actually Means”, a dedicated Journey page and a four-question Before You Begin baseline: current dressing frustrations, what is unclear, what should become easier, and current view of one's style.
- **Draft 3 pp.1–6:** approved subtitle is “A guided workbook for understanding your style, your clothes, and the way you want to get dressed.” Page 3 is What This Blueprint Is; page 5 introduces reusable evidence sets; page 6 is philosophy plus a readiness checklist. It does not contain that four-question baseline.
- **Recommended decision:** preserve the Draft 3 wording, evidence preparation and readiness checklist. Add the four v1.0 baseline questions as a short **optional** before snapshot, with the Journey shown in navigation rather than replacing an approved exercise. Record the baseline as an approved v1.0 addition in the source map.
- **Alternative:** keep Draft 3 front matter entirely unchanged and omit the v1.0 baseline. Owner may instead explicitly approve replacement copy.

### R2 — Garment-length choices

- **Product §09, PDF p.6:** tops separate “cropped” and “waist”; dresses include mini, knee, midi and maxi.
- **Draft 3 p.14:** tops combine “Cropped / waist” and add “Very long”; Dresses / Skirts contains only “Maxi”. The Bottoms list is a separate group and cannot silently be reinterpreted as the missing dress choices.
- **Recommended decision:** keep Draft 3 top choices, including Very long and the combined Cropped / waist choice. Expand Dresses / Skirts to the v1.0 list **Mini / Knee / Midi / Maxi**, retaining Maxi. Treat this as an expressly approved option-list amendment, not an automatic correction.
- **Alternative:** preserve p.14 verbatim, or explicitly approve splitting cropped and waist as well.

### R3 — Consolidated profiles and wardrobe-audit boundary

- **Product §§13, 23, 31, PDF pp.8, 12–13, 15:** profile prompt inventories differ from the later manuscript. The Lifestyle profile explicitly asks “The biggest thing my wardrobe needs more of” and “The biggest thing I have too much of”. Product §25 also mentions overrepresented wardrobe categories.
- **Product §02, PDF pp.1–2:** wardrobe audits, gaps, categories and decluttering belong outside this product.
- **Draft 3 pp.20, 33, 41, 43 and production appendix:** later consolidations intentionally remove duplicate profile structures and keep practicality focused on personal priorities/trade-offs. The Lifestyle profile uses “The biggest lifestyle mismatch I notice is…” instead of the extra too-much/needs-more inventory prompts. Existing frequency and imagined-life observations elsewhere in Draft 3 still remain approved content.
- **Recommended decision:** preserve the consolidated Draft 3 profile fields and mismatch wording. Map equivalent v1.0 outputs to them; do not add another profile or the extra inventory-style prompts. Keep the already-approved frequency/mismatch questions, without introducing wardrobe counts, an audit or gap analysis.

### R4 — Extra discovery prompts in v1.0

These are additions rather than direct philosophical contradictions:

- **Product §17, PDF pp.10–11:** asks for the three strongest visual-dial characteristics. Draft 3 p.25 records nuanced ranges; p.34 separately asks for 3–5 core visual qualities.
- **Product §§21, 42, PDF pp.12, 18–19; Engineering §26, PDF p.11:** explicit colour-behaviour and easiest-way-to-add-colour outputs are not separate prompts in Draft 3 pp.28–30/61.
- **Product §22, PDF p.12:** “If I removed this detail, would the outfit feel less like me?” is not an explicit prompt in Draft 3 pp.31–32.
- **Recommended decision:** allow these specific v1.0 additions as **optional**, contextual controls. Reuse prior colour observations and signatures; do not repeat discovery in Part 5 or replace Draft 3's flexible 3–5 qualities with a mandatory three-word identity. Add no other unsupplied exercises.
- **Alternative:** retain only the Draft 3 prompts and omit these extras.

### R5 — Style Language Dictionary

- **Engineering §37, PDF p.14:** each customer-selected style quality becomes an editable dictionary entry. Product §36, PDF p.17 also shows a quality-to-personal-meaning dictionary.
- **Draft 3 p.51:** gives six named sentence prompts—feminine, polished, casual, sexy, simple, stylish—plus Add Your Own. Page 50 includes the locked Relaxed/Feminine examples, explicitly not prescriptions.
- **Recommended decision:** use the customer's chosen qualities as the main editable dictionary entries; retain the Draft 3 named prompts as optional reflection prompts and preserve the locked p.50 examples. Do not require users to adopt or define an unchosen style label.
- **Alternative:** preserve only Draft 3's fixed prompt structure, using Add Your Own for other selected qualities.

### R6 — Candidate patterns and an assembled Style Brief

- **Engineering §§34, 36, 39, PDF pp.13–14:** surface candidate repeated concepts for confirmation/rejection; optionally suggest quality candidates; generate an editable draft brief from selected data. §25, PDF p.11 also permits descriptive combination wording only when supported by selections.
- **Draft 3 pp.46–49, 54–57:** the customer identifies repeated yeses, writes Pattern / Evidence / Meaning records, chooses core/supporting/accent qualities and writes the brief. Page 47 expressly says the wording and interpretation are the customer's.
- **Recommended decision:** offer **literal, deterministic candidates from recorded selections**, each with source evidence, and require customer confirmation before using one in synthesis. Keep all three p.47 pattern cards and their examples. Offer a customer-invoked “Assemble my draft” using the approved p.54 sentence frame and only confirmed, customer-authored words; leave missing slots blank. Do not infer qualities from body features or convert a dial position automatically into an identity. Keep manual writing/editing available and never silently replace it.
- **Alternative:** keep synthesis and brief writing entirely manual, with earlier-answer reference panels only.

### R7 — Compass scoring contradiction

- **Product §47, PDF p.20:** displays a five-point interpretation (“5/5 — Strong yes”, “4/5 — Likely yes”, “3/5 — Pause and think”, “1–2/5 — Probably not worth buying”, “0/5 — Definitely not for this wardrobe”) without specifying how five criteria become that final score.
- **Engineering §41, PDF pp.15–16 AND Draft 3 p.66:** five separate 0–5 scores; total **0–25**; bands **21–25 / 17–20 / 13–16 / 5–12 / 0–4**. Draft 3 locks one set of anchors/bands.
- **Recommended decision:** use the shared Engineering + Draft 3 **0–25 total and all five approved bands**, with no average, rounding conversion or extra /5 interpretation. Preserve that the score is a decision aid, not a law.

### R8 — Compass questions change the threshold for a purchase

- **Product §47, PDF p.20:** Styling Potential asks “Can I style it at least three ways with things I already own?”; Colour Match simply asks whether it works with the colour direction.
- **Draft 3 p.66:** Styling Potential is “Can I imagine styling this in ways that feel like me?” Colour Match explicitly permits an intentional exception: “Does this colour integrate well with my colour direction, or am I choosing it intentionally as an exception?” These are locked later wording decisions.
- **Draft 3 pp.30/61:** the distinct Rule of Three checks a **colour against three owned items** and is explicitly not a permission slip.
- **Recommended decision:** preserve the exact Draft 3 Compass questions, including the colour exception. Do not introduce a mandatory three-outfit/three-ways threshold or conflate it with the colour Rule of Three.

### R9 — One-glance / final one-page Blueprint fields

- **Product §49, PDF p.21:** requires Personal style rules and Shopping filter on the condensed reference.
- **Draft 3 p.68:** its eight reference rows include the “don't need to become” reminder but no separate rules/filter rows. Those detailed outputs are already present in the p.67 Master Blueprint.
- **Recommended decision:** retain every approved p.68 row and **add compact Personal rules and Shopping filter summaries**, carried from the customer's existing records and editable. Do not replace the permission reminder or restart discovery. Keep the detailed dossier separate; design/test the additional summary rows at mobile and one-page export sizes.
- **Alternative:** retain p.68 unchanged and keep rules/filter only in the master reference, which would be a documented exception to v1.0 §49.

### R10 — Final Personal Style Statement prompts

- **Product §50, PDF p.21:** five closing prompts: “I dress for…”, “I feel most like myself in…”, “My style is a combination of…”, “I don't need my clothes to…”, “I want my wardrobe to help me…”.
- **Draft 3 pp.54, 57, 59, 67:** approved brief, identity and final-statement frames use different wording and allocation; p.67's final frame is “I want to dress in a way that…”. Some ideas overlap, but the five v1.0 prompts are not the approved closing exercise verbatim.
- **Recommended decision:** retain the Draft 3 statement frames and offer the five v1.0 prompts as **optional closing aids**, reusing existing identity/lifestyle/permission answers. Do not make customers redo the discovery or replace their final statement with generated text.
- **Alternative:** retain Draft 3 only and omit the extra closing prompts.

## Compatible requirements: no methodology decision needed

- Preserve the five parts and all 68 source-page references; the website need not have 68 separate screens. v1.0's approximate page targets/75-page ceiling are not a reason to add or delete manuscript exercises.
- Group the work into the six v1.0 sessions: Body; Personality inspiration/preferences; Personality colour/signatures; Lifestyle; Connect the Dots; Build the Blueprint. Retain the source map.
- Use 0–100 internal spectrum values with unchanged Draft 3 endpoints and explicit unanswered states. A stored numerical position is not a “percentage feminine”. Preserve existing responses during migration.
- Use customer-owned, private structured records, autosave, recovery, editable downstream results, no payment integration and no AI classifier.
- v1.0 recommends React/Next/TypeScript/PostgreSQL but expressly says not to replace an established stack unnecessarily (Engineering §04, PDF p.2). The existing Worker/D1/R2 application can therefore be retained. Email/password or magic link is a preferred baseline, not an express ban on the existing secure ChatGPT identity. If independent email-based customer accounts are required for launch, that is a separate provider/access decision, not something to improvise.

## Existing application gaps to address after source approval

These are engineering/product gaps, not approved-source conflicts:

1. **Polished direct PDF export:** current implementation opens browser Print / Save PDF, includes empty fields and repeats some reference sections. v1.0 calls for a generated, properly paginated, completed-information-only PDF and generation/content tests. A server-side approach is preferred. Preserve accurate colour names/swatches and the final document order.
2. **Local recovery:** current failed-save protection is in-memory plus a close warning; v1.0 calls for local recovery when possible. Recovery must be isolated by authenticated user, avoid leaking responses on shared devices, and distinguish local edits from server-confirmed saves.
3. **Small-screen controls:** current table components use horizontal scrolling; v1.0 explicitly forbids requiring that. Use stacked, labelled row editors and test mobile/tablet/desktop.
4. **Evidence granularity:** the current evidence library records images/references and inspiration sorting but not the full per-outfit observation/per-image visual-tag schema in Engineering §§09, 15, 22. Implement optional structured evidence annotations and source-backed aggregation without classifying the customer.
5. **Synthesis:** current code mainly carries forward recorded text; it does not implement the confirmed candidate workflow described in Engineering §34. Its implementation depends on R6.
6. **Dictionary and output data:** current app has fixed dictionary fields and broad object-to-text fallback in some summaries. Use explicit profile/Blueprint schemas, personal dictionary entries and readable sections rather than serialized object keys. Depends partly on R5/R9.
7. **Workload:** remove app-added per-page “Something else I want to remember” prompts from the required flow; these were not supplied manuscript exercises. Preserve any already-saved responses rather than deleting customer data. Keep the three locked Pattern / Evidence / Meaning records.
8. **Assessment metadata:** add explicit assessment identity/status/completion timestamps and meaningful response update metadata, preserving existing account progress through a migration.
9. **Reusable Compass:** keep it independently accessible after completion, with a clean new-item evaluation flow and no accidental reuse of a previous item's scores.
10. **Acceptance testing:** test start/resume/reopen, earlier edits and downstream effects, all sections, editable final output, real PDF generation/content, local recovery, per-user privacy and responsive layouts. Existing DOM/integration checks do not establish browser/mobile visual QA. Current tool discovery still exposes no managed browser control; report that limitation unless tools become available.
